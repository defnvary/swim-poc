# 09 — Nginx, Domains & SSL

`nginx/nginx.conf` (in the repo) is the only hand-written nginx file. Every vhost — platform, app subdomains, custom domains — is **generated** by the api into the `swim-conf` volume (api path `/data/nginx`, nginx path `/etc/nginx/conf.d/apps`) and included by wildcard. One vhost file per host: `<host>.conf`, matching a Domain row 1:1.

## 1. File inventory

| File | Author | Api path | Nginx path |
|---|---|---|---|
| `nginx.conf` | hand-written (repo) | — | `/etc/nginx/nginx.conf` (ro mount) |
| `<host>.conf` | generated by `services/nginx.ts` | `/data/nginx/<host>.conf` | `/etc/nginx/conf.d/apps/<host>.conf` (ro mount) |

## 2. Main config (complete — `nginx/nginx.conf`)

```nginx
# Swim — main config (the only hand-written nginx file)
user  nginx;
worker_processes auto;
error_log /var/log/nginx/error.log warn;
pid /var/run/nginx.pid;

events {
  worker_connections 1024;
}

http {
  include /etc/nginx/mime.types;
  default_type application/octet-stream;

  access_log /var/log/nginx/access.log;

  sendfile on;
  tcp_nopush on;
  keepalive_timeout 65;
  server_tokens off;
  client_max_body_size 10m;

  gzip on;
  gzip_types text/plain text/css application/json application/javascript image/svg+xml;

  # proxy defaults (inherited by all vhosts)
  proxy_http_version 1.1;
  proxy_set_header Host $host;
  proxy_set_header X-Real-IP $remote_addr;
  proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
  proxy_set_header X-Forwarded-Proto $scheme;
  proxy_read_timeout 3600s;   # SSE / log streams
  proxy_send_timeout 3600s;

  # websocket upgrade (no-op for plain HTTP)
  map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
  }

  # TLS defaults
  ssl_protocols TLSv1.2 TLSv1.3;
  ssl_ciphers ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384:ECDHE-ECDSA-CHACHA20-POLY1305:ECDHE-RSA-CHACHA20-POLY1305;
  ssl_prefer_server_ciphers off;
  ssl_session_cache shared:SSL:10m;
  ssl_session_timeout 1d;
  ssl_session_tickets off;

  # unknown Host / SNI gets nothing (nginx:1 is >= 1.19.4)
  server {
    listen 80 default_server;
    listen 443 ssl default_server;
    ssl_reject_handshake on;
    return 444;
  }

  # generated vhosts: platform + app subdomains + custom domains
  include /etc/nginx/conf.d/apps/*.conf;
}
```

Notes:

- The stock image's `/etc/nginx/conf.d/default.conf` is **not** loaded — this file replaces `nginx.conf` wholesale and only includes `conf.d/apps/`.
- `444` closes the connection without a response — no information leak about what this server hosts.
- The long `proxy_read_timeout` keeps SSE log streams alive; per-vhost `proxy_buffering off` makes them stream in real time.
- The wildcard include means nginx starts cleanly with zero vhosts (01 §7 bootstrap requirement).

## 3. Generated vhost templates

### 3.1 Stage 1 — HTTP-only (while `certStatus = pending`)

```nginx
# generated by Swim — do not edit
server {
  listen 80;
  server_name <host>;

  location /.well-known/acme-challenge/ {
    root /var/www/certbot;
  }

  location / {
    default_type text/plain;
    return 200 'certificate pending - retry in a minute';
  }
}
```

During issuance the host serves the ACME challenge and a plain-text placeholder; proxying traffic before TLS exists would produce redirect loops, so none is configured.

### 3.2 Stage 2 — full (after issuance)

App hosts (default subdomain or custom domain):

```nginx
# generated by Swim — do not edit
server {
  listen 80;
  server_name <host>;

  location /.well-known/acme-challenge/ {
    root /var/www/certbot;
  }

  location / {
    return 301 https://$host$request_uri;
  }
}

server {
  listen 443 ssl;
  http2 on;
  server_name <host>;

  ssl_certificate /etc/letsencrypt/live/<host>/fullchain.pem;
  ssl_certificate_key /etc/letsencrypt/live/<host>/privkey.pem;

  location / {
    proxy_pass http://swim-app-<slug>:<port>;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection $connection_upgrade;
    proxy_buffering off;   # SSE-friendly default
  }
}
```

Platform host (`swim.<SWIM_DOMAIN>`):

```nginx
# generated by Swim — do not edit
server {
  listen 80;
  server_name swim.<SWIM_DOMAIN>;

  location /.well-known/acme-challenge/ {
    root /var/www/certbot;
  }

  location / {
    return 301 https://$host$request_uri;
  }
}

server {
  listen 443 ssl;
  http2 on;
  server_name swim.<SWIM_DOMAIN>;

  ssl_certificate /etc/letsencrypt/live/swim.<SWIM_DOMAIN>/fullchain.pem;
  ssl_certificate_key /etc/letsencrypt/live/swim.<SWIM_DOMAIN>/privkey.pem;

  client_max_body_size 10m;

  location /api/ {
    proxy_pass http://swim-api:3000;
    proxy_buffering off;   # SSE log streams
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection $connection_upgrade;
  }

  location / {
    proxy_pass http://swim-api:3000;
  }
}
```

All templates are deterministic functions of `(host, slug, port, SWIM_DOMAIN)` — boot-time reconciliation regenerates byte-identical files (01 §9.3, 07 §10).

A literal upstream is resolved **at parse time**: `nginx -t` fails with `host not found in upstream "swim-app-<slug>"` when that container is not running on `swim-edge`. Stage-2 vhosts therefore require a live app container — see §5.1 for the consequence and the recovery.

## 4. Reload protocol (`services/nginx.ts`)

Every vhost change follows the same sequence:

1. Write the file atomically: write `<host>.conf.tmp`, then `rename()` to `<host>.conf`.
2. `docker exec swim-nginx nginx -t` — on failure, delete the offending file, re-run reconciliation, log `nginx config test failed`, keep the previous running config.
3. `docker exec swim-nginx nginx -s reload`.

`nginx -t` + reload take under 100 ms — no batching, no debounce.

Not-running is not a config error: if the `swim-nginx` container is not up yet (compose
starts it only after api is healthy, `08-docker-strategy.md` §2), steps 2–3 are skipped and
the generated file stays on the volume — nginx reads `conf.d/apps/` when it starts. Deleting
the file in that case would make the platform bootstrap impossible (see §7).

## 5. Domain lifecycle (`routes/domains.ts` + services)

**Add domain** (`POST /api/apps/:id/domains`):
1. Validate syntax + uniqueness (06 §8), insert the Domain row with `certStatus = pending`.
2. Write the stage-1 vhost → reload (§4).
3. Fire-and-forget `issueCert(host, domainId)` — the HTTP response (201) returns immediately.

**`issueCert(host, domainId?)`** (`services/certs.ts`):
1. Run certbot `certonly` (§6).
2. Success → rewrite the stage-2 vhost → reload → `certStatus = issued`, `certIssuedAt = now`, `event('domain.cert_issued')`. With no `domainId` (the platform host, §8) there is no Domain row: the platform stage-2 vhost is written instead and the result is only logged.
3. Failure (DNS not pointing yet, rate limit) → `certStatus = failed`, `event('domain.cert_failed', details: {error})`; the stage-1 vhost stays.

**Delete domain** (`DELETE /api/domains/:id`): remove the vhost file → reload → delete the row. Cert files stay in the volume (certbot self-manages `/etc/letsencrypt/archive`); expiry cleans up the rest.

**Verify** (`POST /api/domains/:id/verify`): resolve `A` records for the host **and** for `swim.<SWIM_DOMAIN>` (the platform's own host); `pointsToServer` = the two record sets intersect. If `certStatus = failed` and DNS is correct → retry issuance once. This is the only retry path (§9). The default `<slug>.<SWIM_DOMAIN>` domain cannot be deleted while the app exists (06 §8).

### 5.1 Known ordering hole — stage-2 vhost written before the app container exists (v1, unfixed)

`issueCert`'s success path (step 2 above) writes the stage-2 vhost at the moment the certificate
is issued. Nothing in the deploy pipeline sequences that against the app container: if the domain
was added **before** the first deploy (or the deploy failed / is still running), the container
`swim-app-<slug>` is absent, `nginx -t` rejects the file with `host not found in upstream` (§3.2),
and §4 step 2 **deletes** it. The Domain row still reaches `certStatus = issued` — the status update
is not gated on the reload, which swallows its own error.

Observable result: the host resolves, its certificate is valid, but no server block matches it, so
the `catch_all` server answers 444 (`NS_ERROR_NET_EMPTY_RESPONSE` / empty reply) and the dashboard
reports the domain as issued.

**Recovery (operator):** get the container running on `swim-edge`, then `docker compose restart api`.
Boot reconciliation step 3 (07 §10) regenerates every vhost from the Domain table — `issued` →
stage 2 — and reloads once; with a resolvable upstream the test passes.

Not fixed deliberately. Candidates for a later phase, each a contract change:
1. rewrite the app's `issued` domains after a deployment reaches `live` (07 §7) — templates stay byte-identical;
2. `resolver 127.0.0.11 valid=10s;` + `set $upstream http://swim-app-<slug>:<port>;` +
   `proxy_pass $upstream$request_uri;` so parse never depends on container state (502 while down,
   self-healing on start) — rewrites the §3.2 template and changes URI handling.

## 6. certbot invocations (exact — via `services/docker.ts runCertbot`)

Issue:

```bash
docker run --rm \
  -v swim_swim-certs:/etc/letsencrypt \
  -v swim_swim-webroot:/var/www/certbot \
  certbot/certbot:latest certonly \
  --webroot -w /var/www/certbot \
  -d <host> \
  --email <SWIM_ACME_EMAIL> \
  --agree-tos --no-eff-email --non-interactive \
  --keep-until-expiring
```

Renew (daily timer):

```bash
docker run --rm \
  -v swim_swim-certs:/etc/letsencrypt \
  -v swim_swim-webroot:/var/www/certbot \
  certbot/certbot:latest renew --webroot -w /var/www/certbot
```

- Volume names come from the platform compose project name `swim` (08 §2): the constants `swim_swim-certs` / `swim_swim-webroot` live in `services/docker.ts`.
- The api and nginx mount the same `swim-certs` volume, so issued certs are immediately visible to nginx (ro) and to path checks in `services/certs.ts`.
- After a successful `renew`, reload nginx once — new certs load without touching any vhost file.

## 7. Platform bootstrap (first boot)

Run by boot reconciliation (07 §10) when the platform cert is missing:

1. Write the stage-1 vhost for `swim.<SWIM_DOMAIN>` → reload.
2. `issueCert('swim.<SWIM_DOMAIN>')` (§6).
3. On success, write the stage-2 platform vhost → reload. On failure, log the certbot error and retry on next boot; the operator checks DNS per `13-setup-guide.md`.

First boot is therefore HTTPS-dark for roughly 30–60 seconds while the certificate issues. The dashboard is unreachable until then — by design, since serving it would require a certificate that does not exist yet.

Ordering note: api reconciles *before* it listens, and compose starts nginx only after api
is healthy (§2, `08-docker-strategy.md`), so on a cold boot nginx is never running during
step 1. Swim writes the stage-1 vhost, lets it stay on the volume, and repeats step 2 once
the `swim-nginx` container is up (checked every 10 s, bounded to 5 minutes). Past that bound
the issuance simply failed and the "retry on next boot" rule above applies — the operator can
also trigger it with `docker compose restart api`.

## 8. Daily timer (`services/certs.ts`)

Runs every 24 h (and once at boot):

1. `certbot renew` (§6) → reload nginx.
2. Image pruning (08 §6), deployment-log pruning (05 §6), event pruning (05 §6), refresh-token pruning (05 §3 step 5).
3. Every error is logged and the timer reschedules itself — the timer never dies.

## 9. Let's Encrypt rate limits & retry policy

- Production limits: 50 certificates per registered domain per week; 5 duplicate certificates per week.
- Swim issues at most once per domain addition; failed issuance retries **only** via the explicit verify endpoint (a user action). There is no automatic retry loop, so a misconfigured domain cannot burn limits.
- `certbot renew` never creates new certificates until ≤ 30 days before expiry — steady-state renewal is invisible to the limits.
- For heavy experimentation, operators should pre-verify DNS before adding domains; `13-setup-guide.md` covers troubleshooting failed issuance.

## 10. DNS expectations (operator-facing)

| Record | Value |
|---|---|
| `swim.<SWIM_DOMAIN>` | A → server IP (required) |
| `*.<SWIM_DOMAIN>` | A → server IP (recommended — covers every future app subdomain) |
| each custom domain | A (or CNAME) → server IP |

A wildcard is recommended but not required — per-app `A` records work equally well because nginx routes by Host header, not by DNS wildcard. The default domain `<slug>.<SWIM_DOMAIN>` is created with the app (05 §1) and its vhost is regenerated by reconciliation.
