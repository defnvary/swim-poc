# 07 — Deploy Pipeline

This document specifies the deploy pipeline end-to-end: queueing, every step, the generated build files, failure handling, and lifecycle operations (stop / start / rollback). `services/deploy.ts` and `services/deploy-queue.ts` implement exactly this and nothing more.

## 1. Status machine

```
queued ──> fetching ──> building ──> deploying ──> live
   │         │            │            │
   └─────────┴────────────┴────────────┴──────> failed
```

- Every transition is written to the Deployment row immediately (the dashboard reflects reality) and announced on live SSE streams as a `status` event.
- `startedAt` is set on `queued → fetching`; `finishedAt` on `→ live` or `→ failed`.
- The api never auto-retries a failed deployment; the user redeploys or the next push triggers again.

## 2. Queueing (`services/deploy-queue.ts`)

- **Per-app serial FIFO**: a `Map<appId, Promise>` chains pipelines; a new deployment for the same app waits until the previous one settles. Arrival order = execution order.
- **Global build semaphore**: at most `SWIM_MAX_BUILDS` (default 2) pipelines may be between `building` and `up -d` at once. The slot is acquired before `docker compose build` and released right after `up -d` — health polling never holds a slot.
- Deployment rows are inserted with status `queued` before enqueueing; the HTTP response (202) returns before any pipeline work starts.
- Manual deploy → 409 if the app already has a deployment in a non-terminal state. Webhook deploys are always accepted and queued (never 409 — GitHub retries otherwise).
- On api boot, any deployment in `fetching | building | deploying` is marked `failed` with error `api restarted during deployment`.

## 3. Step — fetching

Goal: `/data/apps/<slug>/src` contains exactly the target commit.

Target resolution: explicit `commitSha` (manual/rollback) or branch HEAD (default).

First deploy (no `src/.git`):

```bash
git clone --depth 1 --branch <branch> https://x-access-token:<PAT>@github.com/<owner>/<repo>.git src
```

Subsequent deploys (cheaper than re-clone):

```bash
git -C src fetch --depth 1 origin <branch>      # or the explicit SHA
git -C src reset --hard FETCH_HEAD              # or <sha>
git -C src clean -fd
```

Metadata for the row:

```bash
git -C src rev-parse HEAD          # commitSha
git -C src log -1 --format=%s       # commitMessage
git -C src log -1 --format=%an      # author
```

Rules:

- The PAT appears only in the clone URL; the origin remote retains it for refetches.
- `lib/exec.ts` takes a redaction list; any output line containing the PAT (or any other passed secret) is rewritten to `[REDACTED]` before it reaches the deployment log. Mandatory, not optional.
- `--depth 1` bounds disk usage; history is never needed.
- Fetch failure (bad token, repo gone) → deployment `failed` with git's stderr; the previously running container is untouched.

## 4. Step — building

### 4.1 Dockerfile resolution

| buildType | Rule |
|---|---|
| `dockerfile` | `src/Dockerfile` must exist; use it verbatim |
| `node` | `src/package.json` must exist with a `start` script; use the generated Node Dockerfile |
| `static` | `src/index.html` must exist; use the generated static Dockerfile |
| `auto` (default) | try in order: `src/Dockerfile` → `src/package.json` (+ `start` script) → `src/index.html`; none match → `failed` with `no build strategy detected (need Dockerfile, package.json with start script, or index.html)` |

### 4.2 Generated files (outside the cloned source)

```
/data/apps/<slug>/
├── src/               # cloned repo (managed by Swim)
├── compose.yaml       # generated
├── .env               # generated, mode 600
├── Dockerfile.swim    # generated (node | static only)
└── .swim/nginx.conf   # generated (static only)
```

**Node template** (`Dockerfile.swim`; build context = `/data/apps/<slug>`):

```dockerfile
# generated by Swim — do not edit
FROM node:24-alpine
WORKDIR /app
COPY src/package*.json ./
RUN npm ci
COPY src/ ./
RUN npm run build --if-present
ENV NODE_ENV=production
USER node
EXPOSE <port>
CMD ["npm", "start"]
```

Deliberately single-stage: dev deps stay in the image so `npm run build` works without guessing output dirs (`dist` vs `build` vs `out`). Image size is traded for correctness and ~10 lines of generator. Alpine's busybox `wget` satisfies the compose healthcheck.

**Static templates** (`Dockerfile.swim` + `.swim/nginx.conf`):

```dockerfile
# generated by Swim — do not edit
FROM nginx:1-alpine
COPY src/ /usr/share/nginx/html
COPY .swim/nginx.conf /etc/nginx/conf.d/default.conf
EXPOSE <port>
```

```nginx
# generated by Swim — do not edit
server {
  listen <port>;
  root /usr/share/nginx/html;
  index index.html;
  location / {
    try_files $uri $uri/ /index.html;
  }
}
```

### 4.3 compose.yaml template

```yaml
# generated by Swim — do not edit
services:
  app:
    image: swim/<slug>:<sha8>
    build:
      context: .
      dockerfile: Dockerfile.swim
      # repo-provided variant: context: ./src, dockerfile: Dockerfile
    container_name: swim-app-<slug>
    restart: unless-stopped
    env_file: .env
    networks:
      - swim-edge
    healthcheck:
      test: ["CMD-SHELL", "curl -fsS http://127.0.0.1:<port><path> >/dev/null 2>&1 || wget -q --spider http://127.0.0.1:<port><path> || exit 1"]
      interval: 5s
      timeout: 3s
      retries: 3
      start_period: 10s

networks:
  swim-edge:
    external: true
```

Binding facts for the implementer:

- `container_name: swim-app-<slug>` provides the stable DNS name the nginx vhosts proxy to.
- The compose project name is passed on the CLI (`-p swim-app-<slug>`). The project directory (the compose file's dir) makes compose auto-load the sibling `.env`, and `env_file: .env` injects the same vars into the container — one file, both purposes.
- No `ports:` — app containers never publish host ports.
- The healthcheck tries `curl` first, then falls back to busybox `wget` (present in every alpine image). If an app image has neither, the deployment fails with a clear message; generated images always have `wget`.

### 4.4 .env generation

`services/deploy.ts` renders `.env` (decrypt → `KEY=value` lines, mode 600) from the `EnvVar` rows on **every** deployment, right before `compose build`. Regenerated, never patched.

## 5. Build and deploy execution

```bash
docker compose -p swim-app-<slug> -f /data/apps/<slug>/compose.yaml build     # status: building
docker compose -p swim-app-<slug> -f /data/apps/<slug>/compose.yaml up -d    # status: deploying
```

- Both stream stdout+stderr line-by-line into the deployment log and the SSE stream.
- `build` failure → `failed` (exit code + output tail in `error`); the old container keeps serving.
- `up -d` is stop-and-recreate: the new container replaces the old one. Accepted v1 trade-off (no blue-green).

## 6. Health verification

After `up -d`, poll every 2 s:

```bash
docker inspect --format {{.State.Health.Status}} swim-app-<slug>
```

- `healthy` → proceed to live.
- `unhealthy`, or still `starting` after `SWIM_DEPLOY_TIMEOUT` (default 120 s) → `failed` with `container did not become healthy within <N>s (status: <status>)`.
- The failed container is left running for debugging (its logs are reachable in the dashboard); nginx 502s it until a good deploy replaces it.

## 7. Completion

On healthy: deployment → `live`; `app.currentDeploymentId = deployment.id`; `app.status = live`; `event('deploy.live')`; emit `done` on the SSE stream.

Completion does **not** touch nginx: vhosts are written by cert issuance and by reconciliation only (`09-nginx-domains-ssl.md` §5). So an app whose domain was added before its first successful deploy keeps the rejected-vhost state until something rewrites it — boot step 3 (§10) or a manual `docker compose restart api` (`09` §5.1).

## 8. Deployment log format

`/data/logs/deployments/<deploymentId>.log`, appended across all steps:

```
$ git clone --depth 1 --branch main https://x-access-token:[REDACTED]@github.com/acme/demo.git src
Cloning into 'src'...
remote: Enumerating objects: 48, done.
$ docker compose -p swim-app-demo -f /data/apps/demo/compose.yaml build
#1 [internal] load build definition from Dockerfile
...
$ docker compose -p swim-app-demo -f /data/apps/demo/compose.yaml up -d
Container swim-app-demo  Started
[health] healthy after 12s
```

- `$ <command>` headers mark each step (already redacted).
- `[health] <status> after <n>s` summarizes the poll loop (not every poll).
- Non-zero exits append `exit code <N>`.
- `GET /api/deployments/:id/logs` tails this file; live SSE streams appends while the deployment is active.

## 9. Stop, start, rollback

| Op | Behavior |
|---|---|
| stop | `docker compose ... down` (container removed, image kept); `app.status = stopped`; vhosts stay → nginx 502 |
| start | `docker compose ... up -d --no-build` from the persisted compose.yaml and the current deployment's image; 409 if `currentDeploymentId` is null; `app.status = live` |
| rollback | not a special feature: manual deploy with a past deployment's `commitSha`; the image tag `swim/<slug>:<sha8>` makes reruns cache-fast |

## 10. Boot reconciliation (idempotent)

On api start, after migrations:

1. Mark stuck deployments `failed` (§2).
2. `docker network inspect swim-edge || docker network create swim-edge`.
3. Rewrite **all** vhosts from the Domain table, reload nginx once (unchanged files are byte-identical no-ops).
4. Verify the platform cert exists; re-issue if missing before writing the platform SSL vhost.
5. Apps with `status = live` but no running container get `up -d --no-build` (best-effort crash recovery).
